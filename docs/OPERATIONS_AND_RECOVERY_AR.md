# دليل التطوير والصيانة والاستعادة — CAESAR POS

**الغرض:** جعل تحديثات CAESAR POS قابلة للتكرار، ومنع تكرار خلط النسخ أو فقد البيانات. هذا الدليل موجه للمورّد والمطورين والوكلاء الآليين. عند التعارض، المصدر والاختبارات الحالية هما المرجع، لا تقرير تاريخي.

## مصادر الحقيقة ونطاق الإصدار

- فرع التوزيع المعتمد هو `main` في المستودع `Sham4753/kashir-alqaisar-pos`. افحص `git status --short --branch` و`git log -1 --oneline` قبل أي تعديل؛ لا تفترض أن نسخة المستخدم محدّثة أو نظيفة.
- الإصدار البرمجي يحدده `CURRENT_VERSION` في `app/server.py`. لا تستنتج إصدار المنتج من اسم مجلد أو ZIP قديم.
- سلوك التطبيق وقواعد البيانات في `app/server.py`، الصلاحيات في `app/permissions.py`، واختبارات السلوك في `tests/`.
- `AGENTS.md` إلزامي للوكلاء والمهندسين. استخدم هذا الدليل لخطوات التشغيل والإصلاح، و`docs/README_AR.md` للوصول إلى بقية الوثائق.
- لا تنشئ نسخة مشروع أو فرعًا أو حزمة إضافية لمجرد التجربة؛ استخدم نسخة التطوير الحالية وفرع عمل واحدًا، واحتفظ بالمخرجات التي يحتاجها المستخدم فقط.

## أهم قاعدة: البرنامج ليس بيانات المطعم

ملفات البرنامج (المصدر أو `dist\CAESAR_POS`) منفصلة عن **Vault** التي تحتوي بيانات المطعم، قاعدة البيانات، الترخيص المحلي، والسجلات والنسخ الاحتياطية. المسار الافتراضي في Windows هو `C:\CAESAR_Vault`، لكن التطبيق قد يختار مسارًا آخر قابلًا للكتابة أو مسارًا محددًا بمتغير البيئة `CAESAR_VAULT_DIR`. يجب قراءة مسار Vault الفعلي من سجل بدء الخادم أو التشخيص قبل أي استعادة أو ترحيل.

**لا تحذف أو تعِد تسمية أو تستبدل Vault عند إصلاح التطبيق أو تحديثه.** لا تستخدم إجراءات إعداد مطعم جديد لعلاج مشكلة تشغيل أو ترخيص. لا تخلط ملفات Vault من جهازين ولا تستبدل قاعدة البيانات بملف فارغ.

## روتين إصلاح آمن على جهاز عميل

1. **أوقف المحاولات التخريبية.** لا تستخدم `git reset --hard` أو `git clean` أو تحذف مجلدات CAESAR أو تنقلها جماعيًا. لا تستبدل مجلد تثبيت قائم بحزمة كاملة قبل تحديد مكان البيانات.
2. **سجّل الحالة دون أسرار:** إصدار التطبيق، رسالة الخطأ كاملة، مسار تثبيت البرنامج، مسار Vault الفعلي، ومصدر العملية/الاختصار. لا تطلب License Key أو كلمة مرور أو محتوى مفتاح خاص.
3. **أنشئ نسخة احتياطية قبل تعديل الملفات.** من التطبيق استخدم صفحة/إعدادات النسخ الاحتياطي، ثم أغلق التطبيق بالكامل قبل نسخ مجلد Vault كاملًا إلى وسيط أو مجلد احتياطي مستقل. لا تنسخ ملفات SQLite أثناء عمل الخادم؛ ملفات `-wal` و`-shm` قد تكون جزءًا من الحالة الحية.
4. **جرّب على نسخة اختبارية عند الحاجة.** انسخ Vault إلى مسار اختبار منفصل، شغّل التطبيق مع `CAESAR_VAULT_DIR` موجّهًا إلى تلك النسخة، وتأكد أن الاختبار لا يستخدم مسار بيانات المطعم الفعلي.
5. **غيّر ملف البرنامج فقط.** للحزمة المثبتة، استخدم ZIP التحديث اليدوي الرسمي و`Apply_CAESAR_Update.bat`، واختر مجلد التثبيت الذي يحتوي `CAESAR_POS.exe`. أداة التحديث تتحقق من الملفات وتحتفظ بنسخ استرداد للملفات التي تستبدلها؛ وهي مصممة لعدم تغيير Vault والترخيص المحلي والملفات الأخرى. لا تفك ZIP مباشرة فوق المجلد، ولا تشغّل `git pull` على جهاز العميل.
6. شغّل النسخة المحدّثة يدويًا من المسار نفسه، وتحقق من تسجيل الدخول والبيانات والطباعة. إذا اختفت البيانات، **توقف ولا تبدأ الإعداد الأولي**؛ افحص مسار Vault الذي استُخدم بدل إنشاء مطعم جديد.
7. احتفظ بنسخة التثبيت السابقة ونسخة Vault إلى أن ينجح التحقق العملي. لا تحذف النسخ الاحتياطية تلقائيًا بعد أول تشغيل.

| تظهر مطالبة ترخيص بعد تحديث | ميّز بين شاشة الإعداد الأولي وشاشة إعادة التفعيل. إصدار Ed25519 لا يقبل HMAC القديم، كما أن تدوير المفتاح العام يبطل التراخيص القديمة لذلك المفتاح. لا تحذف Vault؛ استخدم شاشة إعادة التفعيل وأصدر ترخيصًا جديدًا لنفس Machine ID من المورّد وفق `docs/LICENSE_ED25519_AR.md`. |

| لا يعمل التحديث أو يفشل التراجع | لا تعِد تشغيله مرارًا. احتفظ برسالة الخطأ ومجلد الاسترداد الذي يطبعه المُحدّث، ولا تحذف Vault أو مجلد الاسترداد. أرسل قائمة الملفات ورسالة الخطأ بعد تنقيح أسماء المستخدمين أو الأسرار. |
| الشعار/QR كبير أو صغير في الإيصال | تحقق من `حجم الشعار على الإيصال` في إعدادات الطابعة واحفظ الإعداد. اختيار الحجم هو المرجع؛ تعرف QR لا ينبغي أن يتجاوز اختيار المستخدم. اختبر المعاينة ثم الطباعة الفعلية على الطابعة المستهدفة. |

## تحديث نسخة المصدر على جهاز التطوير

1. استخدم clone التطوير المعروف، لا clone تجريبيًا جديدًا. افحص:

   ```powershell
   git status --short --branch
   git log -1 --oneline
   git remote -v
   ```

2. إذا ظهرت تغييرات محلية أو ملفات ZIP غير متتبعة، لا تمسحها ولا تستخدم `git clean`؛ افهمها واحفظها قبل التحديث. لا تستخدم `git pull` إلا إذا كانت الشجرة نظيفة، وعلى الفرع المتوقع، وبعد مراجعة التغييرات القادمة. استخدم `git pull --ff-only origin main` فقط في نسخة التطوير.
3. لا تنقل مجلد clone نشطًا بينما نافذة Terminal/PowerShell داخله. تغيير مجلد العمل إلى `C:\` لا يكفي إذا كانت نافذة أخرى أو محرر/مزامنة سحابية تمسك Handle بالمجلد. عند فشل النقل، افحص اسم المسار/العملية أولًا، ولا تكرر النقل أو تقتل عمليات عشوائية. لا حاجة لنقل مسار التطوير لتحديث التطبيق.
4. شغّل الاختبارات، راجع الفرق، وأنشئ فرعًا واضحًا للتغيير. لا تعدّل `main` مباشرة؛ افتح Pull Request وانتظر Windows CI ومراجعة نتائج الاختبارات قبل الدمج.

## بناء نسخة Windows وإصدار العميل

نفّذ من جذر نسخة Windows الكاملة المحدّثة، مع Python والاعتماديات المضمنة:

```powershell
.\python.exe -m unittest discover -s tests -p "test_*.py" -v
node tests\verify_frontend.mjs
.\Setup_CAESAR_OneFile.ps1
```

البناء المستهدف Windows، لذلك لا تُسمِّ فحصًا على Linux بناء Windows فعليًا. راجع نجاح Windows CI ثم نتيجة البناء المحلي. المخرجات العامة المتوقعة:

- `dist\CAESAR_POS\CAESAR_POS.exe` داخل مجلد OneFolder كامل؛ لا توزّع EXE وحده.
- `CAESAR_POS_OneFolder_Commercial_v<version>.zip` لتثبيت جديد.
- `dist\CAESAR_POS_Update_v<version>.zip` لتحديث تثبيت قائم.

لعميل لديه تثبيت وبيانات قائمة، استخدم **حزمة التحديث** لا حزمة التثبيت الجديد. افحص محتويات ZIP لضمان غياب Vault العميل، قواعد البيانات، ملفات الترخيص المجهزة، المفتاح الخاص، ومولّد الترخيص. اختبر ZIP التحديث على نسخة تثبيت وVault اختبارية قبل نشره في GitHub Releases. انشر أصل ZIP فقط، مع رقم إصدار واضح وتعليمات النسخ الاحتياطي؛ لا تطلب من العملاء استنساخ المصدر أو استخدام Git.

## إصدار التراخيص وأمن المفاتيح

- التوقيع الحالي Ed25519. المفتاح العام فقط في `app/license_public_key.pem` ويمكن نشره.
- المفتاح الخاص المشفّر وعبارة مروره ملك للمورّد، ويظلان خارج المستودع وخارج حزم العميل. لا تنسخهما إلى محادثة أو تقرير أو ZIP، ولا تسجل قيمة عبارة المرور.
- أداة المورّد هي `tools\Issue_CAESAR_License.cmd`: أدخل Machine ID، ثم أرسل للعميل License ID وLicense Key فقط. لا تصدر ترخيصًا قبل التحقق من أن المفتاح الخاص المحلي يقابل المفتاح العام المضمّن في نسخة العميل الحالية.
- لا تنشئ زوج مفاتيح مع كل تحديث. تدوير المفتاح قرار أمني منفصل يبطل الرخص الموقعة بالمفتاح السابق ويستلزم خطة لإعادة إصدار الرخص.
- راجع `docs/LICENSE_ED25519_AR.md` للتفاصيل. لا تضمّن أداة الإصدار أو ملف المفتاح الخاص في حزمة العميل.

## مراجعة التغيير قبل الدمج

```sh
git diff --check
git status --short --branch
git diff --stat
git diff
```

تحقق من أن التغيير لا يضم بيانات مستخدم، ملفات Vault أو SQLite/WAL/SHM، سجلات، أسرار، مفتاحًا خاصًا، أو ZIP عميل محليًا. شغّل الاختبارات المركزة ثم المجموعة الكاملة المناسبة، ودوّن بدقة ما نجح وما لم يُختبر. لا تدّعِ نجاح Windows CI أو اختبار جهاز أو طابعة لم يُنفّذ. افتح PR، انتظر Windows CI، وادمج بعد نجاح الفحوص المطلوبة فقط.

## النسخ الاحتياطي والاستعادة

- احفظ نسخة يومية من بيانات المطعم في مكان منفصل عن الجهاز التشغيلي، وتحقق دوريًا من إمكانية قراءة النسخة واستعادتها على بيئة اختبار.
- الاستعادة لا تتم فوق Vault الحية مباشرة قبل حفظ نسخة أخرى. اختبر الاستعادة إلى مسار منفصل، تحقق من الفواتير والمستخدمين والإعدادات، ثم قرر النقل بعد إغلاق التطبيق.
- لا تستخدم `CAESAR_Vault` كنسخة احتياطية وحيدة. لا ترفع نسخة احتياطية إلى GitHub، ولا ترسل قاعدة البيانات أو بيانات الزبائن عبر قنوات غير آمنة.
